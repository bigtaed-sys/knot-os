# KnotOS v0.2 — Implementation Plan

## Context

v0.1 shipped a working Wi-Fi extender with first-run wizard, web UI, plugin scaffold, and update tooling. v0.2 builds on that base by turning KnotOS from a "Wi-Fi pipe with a UI" into a **router with real awareness of who is using it**.

The two flagship features chosen for v0.2 are:

1. **Per-device profiles** — devices on the LAN have stable identities (name, icon, last-seen), and each one can have a schedule (e.g. "kid's tablet, no internet 22:00–07:00") and a DNS profile.
2. **Ad-block / DNS filter** — built-in Pi-hole-equivalent: configurable blocklists, NXDOMAIN response for blocked domains, query log with per-device attribution, stats in the UI.

These two features share infrastructure (DHCP lease tracking, MAC→device mapping, a smarter DNS layer) and are presented as a single cohesive UX in the new "Устройства" / "Devices" page.

Out of scope for v0.2 (deferred to v0.3+):

- HTTPS / signed updates / encrypted PSK at rest — security hardening pass
- Pi 4/5 support — focus stays on Zero 2W
- USB-Ethernet WAN / full-router role — repeater role only
- Mesh / multi-node discovery
- Guest network with QR
- Real plugin runtime (gRPC, lifecycle) — features stay built-in

## Architecture decisions

### DNS layer: replace dnsmasq's DNS, keep its DHCP

dnsmasq does both DHCP and DNS today. For v0.2 we need a smarter DNS — per-device awareness, blocklist lookup, query logging — which dnsmasq's `address=/...` syntax doesn't comfortably support at scale (100k+ blocked domains).

Plan: split the two functions.

- **DHCP** stays in dnsmasq (it's good at it, leases parse cleanly).
- **DNS** becomes a Go service inside `knotd`, using `github.com/miekg/dns` for a tiny resolver. dnsmasq is reconfigured to advertise the Pi as the DNS server (already does), but no longer answers DNS itself — it's bound to `:53` only on the DHCP side. The Go resolver listens on `192.168.42.1:53`.

The Go resolver:
- Looks up the source IP in the DHCP lease table → MAC → device profile.
- If the device's profile blocks the queried domain (in any of its blocklists), returns `NXDOMAIN`. Otherwise forwards to the configured upstream (default 1.1.1.1/8.8.8.8) and caches.
- Logs every query (domain, source MAC, blocked y/n, response time) into a ring buffer for the UI.

### Device registry

- Source of truth: dnsmasq's lease file (`/var/lib/misc/dnsmasq.leases`, watched by inotify).
- Augmented with `/etc/knot/devices.yaml` for user-set names, profile assignments, and MAC overrides.
- In-memory `deviceregistry` package with a debounced flush back to disk on changes.

### Schedule enforcement

- Each device profile has a list of `BlockWindow{ days, start, end }` rules.
- A scheduler goroutine in knotd ticks every 30s, computes "is this MAC currently blocked?" for each known device, and updates an `nftables` named set `knot_blocked_macs`.
- The forward chain gains a rule: `ether saddr @knot_blocked_macs drop`. Devices in the set get no internet, but they keep their LAN access (DHCP, DNS, KnotOS UI) — so the user can still see them in the dashboard.

### Blocklist sources

- Default: StevenBlack/hosts (~150k entries, ad+tracker focus). Pinned URL.
- Optional: extra URLs the admin can add (e.g. malware, NSFW lists).
- Cached at `/var/lib/knot/blocklists/<source-hash>.txt`. Refreshed daily on a timer.
- Loaded into a memory-efficient bloom filter + hash set in the Go resolver. Estimated RAM: ~5–10 MB for 200k entries — fine on Zero 2W's 512 MB.

## Milestones

Each milestone is one to three commits, like v0.1.

### M9 — Device registry

- `core/internal/deviceregistry/`: in-memory store, lease-file watcher, YAML persistence.
- API: `GET /api/devices`, `GET /api/devices/:mac`, `PATCH /api/devices/:mac` (set name, profile).
- UI: new sidebar item "Устройства" with a list page (icon, name, MAC, IP, online dot, last-seen).

### M10 — Profiles and schedules

- Profile schema: `Profile { id, name, schedule[], dns_blocklists[], dns_upstream? }`.
- Built-in profiles: `default`, `kids` (no internet 22:00–07:00, ad-block on), `guest` (no internet outside of LAN, only main DNS).
- nftables ip-set / ether-set wiring; scheduler tick.
- API: `/api/profiles` CRUD.
- UI: profile picker on the device detail page, schedule editor (visual week grid).

### M11 — DNS resolver + ad-block

- `core/internal/dns/` package: miekg/dns server, blocklist loader, upstream forwarder, in-memory cache, query log ring buffer.
- Switch dnsmasq to DHCP-only mode in `applyExtender`.
- Blocklist downloader: scheduled fetch + parse + hash into compact set.
- API: `GET /api/dns/stats`, `GET /api/dns/queries?limit=N&since=...`.

### M12 — Ad-block UI + polish

- New sidebar item "Защита" / "Protection" with stats: queries / blocked / top domains / per-device breakdown.
- Charts (sparkline of blocked % over 24h, top-10 blocked domains by count).
- Per-device DNS profile picker on device detail page.
- Translations (RU + EN) for all new strings.

### M13 — v0.2.0 release

- Real-hardware test pass against the v0.2 acceptance checklist (analogous to v0.1's 14-step list).
- Update CHANGELOG with v0.2.0 notes.
- Tag v0.2.0, GitHub release.

## Acceptance test (v0.2.0 on real Zero 2W)

1. Wizard runs, extender role active.
2. New "Устройства" page lists every device that has connected (phone, laptop) — names auto-derived from DHCP hostname.
3. Rename a device, verify the name persists across knotd restart.
4. Apply the "kids" profile to a test device. Within 30s, that device loses internet (browsing fails) but still sees the KnotOS UI.
5. Wait until past the schedule's end time → the device gets internet back, no manual intervention.
6. From a clean device, browse to a known ad-serving domain (`doubleclick.net`). Browser dev tools show NXDOMAIN.
7. Same device on the `default` profile (no blocklist) → ad-serving domain resolves normally.
8. Open "Защита" page → see total queries, % blocked, top-blocked list updates as you browse.
9. Add a custom blocklist URL → after refresh interval (or manual "Refresh now"), entries from that list also block.
10. Reboot device → all devices, profiles, schedules, blocklists survive.

## Risks and unknowns

1. **Lease-file format quirks.** dnsmasq leases include hostname only when DHCP client supplies it; iOS/Android sometimes don't. Need fallback (vendor MAC OUI lookup) for "Unknown device".
2. **DNS resolver memory.** A naive blocklist as `map[string]bool` of 200k entries is fine (~10 MB) but a custom hashed set is better. Need to benchmark on Zero 2W.
3. **Cache invalidation on profile change.** When a device's profile changes mid-session, existing TCP connections continue through the old policy. Acceptable — new lookups respect the new profile, and TTL-driven cache flushes within seconds.
4. **DNSSEC.** Out of scope for v0.2; the resolver forwards any record types upstream as-is, no validation.
5. **DNS-over-HTTPS clients (Firefox, Chrome).** Bypass our resolver entirely. Detection (block known DoH endpoints) is a v0.3 problem.
