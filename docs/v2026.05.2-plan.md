# v2026.05.2 — план

Тема: **«Достоверность и наблюдаемость»**. v2026.05.1 закрыл core-функциональность (LAN + WG-сервер + VPN-клиент по подпискам). v2026.05.2 делает три вещи:

1. Превращает knotd в честный наблюдаемый роутер — за каждым устройством и тоннелем виден реальный трафик в байтах/секунду, а не только статус.
2. Чинит весь класс «после Apply что-то не так / не сразу» багов — добавляет idempotent watchdog, transactional apply с rollback, health-checked restarts.
3. Делает первое нативное расширение KnotOS наружу: backup/restore конфигурации, чтобы переезд между Pi (или восстановление после убитой SD-карты) занимал минуту, а не вечер.

## Флагманские фичи

### M32 — per-device bandwidth metering

Для каждого устройства в реестре считать live-bandwidth (current Kbps in/out) и накопленный объём (MB total за день / неделю / месяц). Источник: `nftables` named counters per source IP, опрашиваемые каждые 2 секунды через `nft -j list counter`. Хранить в кольцевом буфере на 24 часа в памяти + персист каждые 5 минут.

UI: каждая строка `/devices` получает sparkline с последним часом + цифру «12.4 Mbps», device-detail page получает график сутки/неделя/месяц. Telegram `/devices` — те же sparkline'ы из юникод-блоков.

### M33 — transactional Apply с health check + rollback

Сейчас apply — последовательность шагов; если шаг 7 из 10 падает, система остаётся в наполовину-применённом состоянии (как у тебя со setup→router). Перепишу:

1. Перед каждым `Apply` — снапшот running state в `/run/knot/apply.snapshot.json`
2. После `Apply` — health check (ssid поднялся? AP отвечает? DNS резолвит? WAN dhcp leased?)
3. Если health не прошёл за 30 сек — автоматический rollback на снапшот
4. UI получает `apply_id`, через `GET /api/apply/{id}` смотрит прогресс, rollback или success

Это закрывает целый класс «не работает после apply» багов раз и навсегда.

### M34 — config backup/restore + Pi miner mode

Один эндпоинт `POST /api/system/backup`: возвращает `.knot-backup` (зашифрованный AES-256-GCM tarball всего `/etc/knot/` + `/var/lib/knot/` + selected runtime state). Парный `POST /api/system/restore` — принимает файл, раскатывает, перезагружает knotd.

UI кнопка «Скачать резервную копию» в System, drag-and-drop поле в setup wizard для восстановления.

«Pi miner mode» — секретный второй слой: текущий live-config можно поставить на любую другую Pi-инсталляцию через копию SD на новый Pi → `restore` → готово, новая железка с нашими профилями/устройствами/подписками без перенастройки.

## Operational

### M35 — observability log

Один долгоживущий лог-стрим в `/run/knot/audit.log`: каждый `Apply`, каждый `Refresh`, каждое изменение профиля, каждый WAN up/down. Telegram `/log` показывает последние 20. UI System → Журнал → таблица + фильтр по типу.

Это нужно потому что сейчас отладка идёт через `journalctl -u knotd` — для пользователя невозможно. Audit log — наша версия event log, без шума ядра.

### M36 — Setup wizard: полный реворк

Текущий wizard — 663 строки на одной странице, 5 шагов, голые поля без контекста, никакого визуала, никаких объяснений. Пользователь, который купил Pi и впервые увидел экран KnotOS, не понимает что выбрать и почему.

Полностью переписать с нуля. Восемь шагов, каждый — отдельный экран с понятной целью.

**1. Welcome screen — NEW**
> Привет! 👋 Я KnotOS — твой домашний роутер.
> Сейчас за 3–5 минут настроим всё, что нужно.

- Анимированный Pi с подсветкой портов (Ethernet, Wi-Fi, USB)
- Список того, что будет дальше: «выбрать роль → подключиться к интернету → задать имя сети → готово»
- Big-button «Поехали» внизу
- Внизу мелким — оценка времени, ссылка на доку

**2. Hardware inventory — NEW (автоматический)**
> Я посмотрел, что у тебя есть.

- Auto-detect: модель Pi (Zero 2W / 4 / 5), наличие Ethernet, состояние Wi-Fi-чипа
- Визуальная диаграмма обнаруженного железа с подсветкой того, что подключено:
  ```
  [Pi 4]  Ethernet (WAN) ─── ✓ кабель
          Wi-Fi             ─── ✓ работает
          USB-Ethernet      ─── ─ не подключено (опционально)
  ```
- Если нет WAN-кабеля и роутер выбран — кнопка «Подключи кабель и обнови» вместо ошибки
- Текст: «На основе того, что есть, ты можешь сделать одно из следующего…»

**3. Choose role — большие карточки + визуализация**
> Какую роль выберешь?

Вместо radio-buttons — три большие карточки на всю ширину, каждая с:
- Иконкой
- Названием («Wi-Fi роутер» / «Wi-Fi повторитель»)
- Маленькой ASCII/SVG диаграммой что куда воткнётся:
  ```
  Роутер:     [интернет] ──cable── [Pi] ──Wi-Fi── [твои девайсы]
  Повторитель:           [роутер провайдера] ──Wi-Fi── [Pi] ──Wi-Fi── [твои девайсы]
  ```
- Одно предложение зачем: «Полноценный домашний роутер — Pi подключается к ISP-кабелю и раздаёт Wi-Fi всему дому»
- Аккордеон «Не знаешь что выбрать?» с decision tree: 3 вопроса → ответ
- Disabled-состояние с объяснением: «Роутер недоступен — нет Ethernet порта»

**4. Connection (адаптивно от роли) — smart defaults**

*Роутер:*
- Auto-detect WAN-типа (попробовать DHCP, услышать PPPoE-Discovery, посмотреть IP) — заняло 5 секунд при загрузке этого шага
- «Похоже у тебя обычный кабельный интернет (DHCP). Просто нажмите Далее.» — kill 80% сложности для типового пользователя
- Если PPPoE/L2TP — раскрылась форма с логин/пароль с подсказкой «эти данные дал провайдер при подключении, обычно в договоре»

*Повторитель:*
- Auto-scan при заходе на шаг
- Список сетей карточками: SSID + signal-bars + lock-icon + «Соседи на канале 6: много / мало»
- Tap на карточку → раскрывается поле пароля
- «Не вижу свою сеть» → подсказки (далеко от роутера? 5 GHz — мы пока не умеем?)

**5. Wi-Fi для твоих устройств — live preview**
> Как назовём твою сеть?

- Поле SSID с live-валидацией (32 байта, кириллицу — норм)
- Поле пароля с strength meter (zxcvbn-style, на клиенте)
- **Live QR справа от формы** — обновляется while typing, предпросмотр того что увидят гости
- Channel — разворачиваемая секция:
  - По умолчанию закрыто, написано «Канал: авто (рекомендуется)»
  - При раскрытии — результат scanner'а в виде столбиков: «канал 1 (8 соседей), 6 (12), 11 (2)» с подсветкой рекомендованного
- На Pi 4/5 ещё опция band 2.4/5 GHz (M37 даёт это)

**6. Админка**
> Пароль для входа в управление KnotOS.

- Поле пароля + подтверждение
- Strength meter
- Под полем мелким: «Это НЕ пароль от Wi-Fi. Этим паролем ты заходишь сюда, в эту админку, со своего ноутбука или телефона.»
- Опциональная карточка снизу: «Также подключить Telegram-бот?» с галочкой → если да, после Apply дополнительный экран с PIN

**7. Review — «вот что я сейчас сделаю»**
> Готово! Прочитай и подтверди.

- Визуальная диаграмма финального состояния (та же что в шаге 3, но с подставленными SSID/паролем/каналом)
- Bulleted-список изменений: «Создам Wi-Fi сеть „MyNet“ на канале 6», «Подключусь к интернету через Ethernet», и т.д.
- Информационный блок: «Если что-то пойдёт не так за 30 секунд — я откачусь обратно автоматически» (tie-in M33)
- Кнопка «Применить настройки»
- Кнопка-ссылка «Назад поправить» наверху

**8. Apply progress — LIVE streaming**
- Использует SSE / WebSocket (или polling) `GET /api/apply/{id}/events`
- Шаги показываются один за другим с галочками:
  ```
  ✓ Сохранил конфигурацию
  ✓ Поднял точку доступа «MyNet»
  ⏳ Проверяю интернет…
  ⏳ Готовлю админку…
  ```
- Если health-check упал → красная плашка «Что-то не получилось: <reason>. Откатился на прежнюю настройку, попробуй ещё раз.»
- Если success → 3-секундный countdown «Перенаправляю в админку…» + кнопка «Зайти сейчас»
- На фоне — анимация (spinner / dots / progress bar плавно бежит)

**Дизайн-принципы (общие):**
- **Card-based + slide transitions** — каждый шаг это card по центру, переходы между шагами — плавный slide
- **Прогресс-бар сверху** — не «Step 3 of 5», а 8 точек с иконками: ●●●○○○○○ + подпись текущего
- **Inline-help везде** — `?` иконка рядом с КАЖДЫМ полем, по тапу раскрывается tooltip с объяснением
- **Mobile-first** — большинство юзеров делают setup с телефона (ноутбук занят подключением к knot-* AP), макет рассчитан в первую очередь под 375px
- **Dark mode** — нативно с самого начала
- **Иллюстрации / иконки** — реальные SVG для Ethernet кабеля, Wi-Fi сигнала, Pi-моделей
- **Тон** — тёплый, дружелюбный, на «ты» (как в Telegram-боте после M30 polish). Никаких технических терминов без объяснения. «WAN» = «выход в интернет», «PSK» = «пароль для Wi-Fi», и т.д.
- **Полная ru/en локализация**, plural-aware

**Технически:**
- Каждый шаг — свой Svelte-компонент в `ui/src/routes/setup/steps/`
- Общий store с прогрессом (Svelte 5 runes)
- API не меняется (тот же `POST /api/setup/complete`), но добавляется live-progress endpoint (`GET /api/apply/{id}/events`) для шага 8 — это ложится на M33 transactional apply
- Иллюстрации — inline SVG в компонентах, не зависим от внешних ассетов

**Объём работы:** ~3-4 дня. Самый большой компонент v2026.05.2 после M33.

### M37 — wireless 5 GHz support

Текущий KnotOS — 2.4 only. На Pi 4/5 чипсет умеет 5 GHz. Добавить:
- `band: "5"` для AP конфига
- Channel list по странам (DFS / non-DFS)
- Hostapd с `ieee80211ac=1`, `vht_capab` подбор по чипу
- Сканер работает на обоих диапазонах
- UI показывает оба band'а в одном устройстве, можно сделать dual-band SSID (одинаковое имя на 2.4 + 5)

## Что туда НЕ войдёт

- IPv6 first-class (отдельная тема, требует переработки nftables/dnsmasq, M28-уровня объёма работ)
- Plugin marketplace — преждевременно, пока есть 4 плагина
- Mesh / extender topology через MAC-roam — нужна вторая Pi для тестов
