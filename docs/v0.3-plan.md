# KnotOS v0.3 — Implementation Plan

## Context

v0.1 made a Wi-Fi extender. v0.2 turned it into a router that knows
*who* is using it: per-device profiles, schedules, ad-block, query
log. v0.3 lifts the two ceilings v0.2 walked into:

1. **Hardware ceiling.** Zero 2W's single-radio repeater is great as
   a "drop in next to a weak signal" device, but it's a glass ceiling
   for throughput (one channel, ~50%) and for what we can offer
   (no real WAN, no second radio). v0.3 adds the **full-router role
   on Pi 4 / Pi 5 with a USB-Ethernet dongle** — Ethernet WAN on
   `eth0`, AP on `wlan0`, optional second AP on a USB Wi-Fi.
2. **Trust ceiling.** Today the dashboard is HTTP, Wi-Fi PSKs sit
   in cleartext under `/etc/knot/`, sessions die on restart, and the
   updater accepts any blob the user uploads. v0.3 closes those:
   **HTTPS by default, encrypted secrets at rest, signed updates,
   persisted sessions.**

Everything else stays in the v0.4 backlog: real plugin runtime
(gRPC, lifecycle), mesh, guest QR, presence detection beyond "lease
is valid", DoH-bypass blocking, Armbian profiles.

The two flagship features share infrastructure — the full-router
role wants HTTPS more than the extender did (admin UI now sits on
a routable LAN, not just the AP's `192.168.42.0/24`), and signed
updates rely on the same TLS PKI we generate for HTTPS. That's why
they ship together.

Out of scope for v0.3 (deferred to v0.4+):

- **Plugin runtime**: gRPC over Unix socket, lifecycle (start/stop/
  restart), capability gating, UI extension points. Plugins still
  install + appear in the menu but stay metadata-only.
- **Mesh / multi-node discovery**.
- **Guest network with QR onboarding** (low value until we have an
  AP on a second radio, which only Pi 4/5 + USB Wi-Fi unlocks).
- **DoH-endpoint blocklist** (Firefox / Chrome bypass detection).
- **Armbian / non-Pi build profile** — gated on confirming
  AP-mode Wi-Fi support per board.
- **DNSSEC validation** on the resolver — forwarder still passes
  records through unchanged.

## Architecture decisions

### TLS and the local CA

Self-signed-per-device with a captive root that the user installs
once. The wizard generates an ECDSA P-256 root CA on first boot,
issues a leaf for the device's hostname (`knot.local`,
`<device>.local`, the LAN gateway IP), and serves the root from
`http://<ip>/setup-ca.crt` on the captive-portal interface during
setup. The daemon listens on both 80 (HTTP, redirects to HTTPS) and
443 (HTTPS) once a cert exists; in setup mode 80 keeps serving the
wizard so onboarding doesn't need a trust dance.

Why not Let's Encrypt: a router on a private LAN has no public
DNS name, no port-forward, and frequently no internet at the moment
HTTPS is most important (during setup). Why not skip TLS until v0.5:
a v0.3 full-router exposes its admin UI on `192.168.1.1`-style
addresses that overlap with every other "router admin" page on the
planet, making "is this really my router" a real concern.

The cert+key live under `/etc/knot/tls/` (root-only, 0600). The
root cert is also dumped to `/boot/firmware/knot-root-ca.crt` so a
user with SD-card access can recover trust without the UI.

### Encrypted secrets at rest

A Linux-keyring-backed "device key" (kernel keyring of type
`logon`, persisted across reboots via `systemd-cryptsetup` style
seeding from `/boot/firmware/knot-key-seed`) wraps Wi-Fi PSKs in
the on-disk config. The wrapping is AES-256-GCM with a per-secret
nonce; YAML stores the wrapped form in a tagged-string scalar so
config files remain hand-editable for everything that isn't a
secret. Loading falls back to plaintext for legacy configs from
v0.1/v0.2 and re-saves them encrypted on the next config write.

What this *isn't*: protection against an attacker who has root on
the running system. It is protection against a stolen SD card (the
seed lives on the FAT partition, but the kernel keyring entry is
created from seed-plus-machine-id, where the machine-id rotates on
re-flash). Per-CPU TPM-backed secrets are a v0.5 problem.

### Full-router role

The new role is `wifi-router`, joining `setup` and `wifi-extender`.
Apply pipeline:

1. Detect WAN interface (USB Ethernet via udev rule
   `usb*/eth*` — most TP-Link / Plugable adapters land as `eth0`).
2. Configure DHCP client on WAN, NAT from LAN to WAN.
3. AP on `wlan0` with the user's chosen channel (no longer pinned
   to the upstream's, since there's no upstream Wi-Fi in this role).
4. dnsmasq DHCP on the LAN side, knotd DNS on the gateway IP
   (same setup as `wifi-extender`).
5. Optional second AP on a USB Wi-Fi (`wlan1`) — tagged as guest
   network, isolated VLAN inside the bridge. **Skipped if absent.**

The role choice happens during the setup wizard:

- Boot detects "Pi 4 / Pi 5 *and* a USB-Ethernet dongle is plugged
  in" → wizard shows both extender and router as options.
- Pi Zero 2W or no Ethernet dongle → wizard shows extender only
  (current v0.2 behavior unchanged).

The "either-or" logic lives in `core/internal/network/capability/`.

### Signed updates

`update-knot.ps1` already pushes a fresh `knotd` binary to the
device. v0.3 makes that path verify a signature: the new binary is
accompanied by a detached `.sig` (Ed25519) signed by a release key
whose public half is baked into the running binary at build time.
A second public key (the user's "rescue key", optional, generated
on first run and shown once) authorizes self-built binaries.

Without a valid signature, knotd refuses the update with a clear
error in the System page. CI signs every release with a key whose
private half lives in GitHub Actions secrets.

### Persisted sessions

Sessions move from a `map[string]Session` into a tiny BadgerDB
table at `/var/lib/knot/sessions.db`. TTL stays at 24h; logout
revokes; reboot no longer kicks the user out mid-task. BadgerDB
because it's pure Go, single-binary-friendly, and we already use
similar embedded stores elsewhere.

### Presence detection (cheap version)

`Online()` today asks "is the DHCP lease valid?", which over-
reports — a phone in another room with an unexpired lease shows as
online. v0.3 augments with a 60s ARP probe of every leased IP via
`/proc/net/arp`. The lease is the floor (offline if the lease
expired); ARP is the ceiling (offline if no recent ARP entry).

Stops short of `iw station dump` because that needs the AP to be
up and only sees Wi-Fi clients, not Ethernet. Polls `/proc/net/arp`
because it's free, kernel-maintained, and works in both extender
and router modes.

## Milestones

Each milestone is one to three commits.

### M14 — TLS + local CA

- `core/internal/tls/`: ECDSA P-256 keypair generation, self-signed
  root + leaf issuance, on-disk persistence under `/etc/knot/tls/`.
- `core/internal/httpserver`: dual-listener (80 redirects to 443
  outside `setup` role; 80 stays open in setup).
- Wizard exposes `/setup-ca.crt` for download.
- API: `GET /api/tls/info` (cert fingerprint + expiry), `POST
  /api/tls/regenerate` (re-issue the leaf without rotating the root).
- UI: System → Security card with the fingerprint, expiry, and a
  "Download root certificate" button.

### M15 — Encrypted secrets at rest

- `core/internal/secrets/`: keyring seed bootstrap, AES-GCM wrap /
  unwrap, transparent YAML-aware encoding (`!secret <base64>`).
- Migration: on load, plaintext secrets get re-saved encrypted on
  the next write. No config-file format break.
- Tests against a fake keyring so the package is testable on
  non-Linux dev boxes.
- Wired into the existing config save path; `update-knot.ps1`
  doesn't need to change.

### M16 — Full-router role on Pi 4 / Pi 5

- `core/internal/network/capability/`: USB-Ethernet detection
  (`/sys/class/net/<iface>/device/uevent`), Pi-model probe.
- `apply_router.go` next to `apply_extender.go`: hostapd config
  for an AP on a fixed channel, NAT config for `eth0` ↔ `wlan0`,
  optional `wlan1` guest AP.
- Wizard adds a "Что вы делаете?" / "What are you doing?" step
  with two cards (Extender / Full router) when both are eligible.
- Acceptance: real Pi 4 with a Plugable USB-Ethernet adapter:
  WAN comes up via DHCP, devices on the AP get internet, ad-block
  still works, the LAN admin UI is reachable at the gateway IP
  over HTTPS (after M14).

### M17 — Signed updates + persisted sessions

- Ed25519 verification in the existing update path; release key's
  public half goes into `core/internal/update/keys.go` at build
  time via `-ldflags -X`.
- Rescue-key generation on first run (root-only file at
  `/etc/knot/rescue.pub`, displayed in the System page once).
- Sessions move to BadgerDB at `/var/lib/knot/sessions.db`.
- CI workflow signs `knotd` + emits `knotd.sig` alongside the
  release artifact.

### M18 — Presence detection + UX polish

- ARP-table watcher reads `/proc/net/arp` every 30s; merges with
  lease state to drive the per-device "online" pill more honestly.
- Forget-device UI gets a "stale" badge ahead of the button when
  a device hasn't ARPed in >30 days, so the user knows it's safe
  to remove.
- Misc: i18n pass for new strings, dashboard tile redesign for
  the router role (WAN status replaces uplink card).

### M19 — v0.3.0 release

- Real-hardware acceptance pass on both Zero 2W (extender) and a
  Pi 4 + USB Ethernet (router).
- Update CHANGELOG.
- Tag v0.3.0, GitHub release with signed `knotd` binary +
  flashable image artifact.

## Acceptance test (v0.3.0)

Two passes — one on Zero 2W (extender role, regression), one on
Pi 4 + USB Ethernet (new router role).

Zero 2W (regression):

1. v0.2 acceptance checklist still passes end-to-end.
2. After the wizard, hitting `http://<ip>/` redirects to
   `https://<ip>/`. Browser shows "untrusted" until the user
   downloads + installs `setup-ca.crt`, then green padlock.
3. Wi-Fi PSK in `/etc/knot/config.yaml` is `!secret …` instead of
   plaintext.
4. Reboot the Pi mid-session → still logged in afterwards.
5. Try uploading a tampered `knotd` (any byte flipped) → System
   page rejects with "signature invalid".

Pi 4 + USB Ethernet (router):

1. Wizard offers both Extender and Router; pick Router.
2. Pick a channel + AP SSID; apply.
3. Plug a phone into the AP → DHCP lease, ad-block + per-device
   profiles work the same as on Zero 2W.
4. Plug a laptop's Ethernet into the Pi's onboard NIC (acting as
   LAN, since `eth0` is the USB dongle for WAN) → it gets a lease
   and reaches both the UI and the internet.
5. Pull the USB Ethernet dongle → dashboard shows "WAN down",
   internal traffic still works, AP stays up.
6. Plug a USB Wi-Fi (Realtek 8821CU) → wizard's
   "Add a guest network" toggle becomes available; create a
   guest SSID; verify it isolates from the main LAN.

## Risks and unknowns

1. **USB-Ethernet driver coverage.** Plugable / TP-Link UE300
   (Realtek 8153) is well-supported on Pi OS Lite arm64. Cheaper
   ASIX adapters work but sometimes need a `dwc2` USB mode change
   on the Pi 4. Need a hardware compatibility doc.
2. **Self-signed cert UX on iOS.** Installing a root CA on iOS
   takes a Profile + a manual "trust" toggle three menus deep.
   Document with screenshots; don't try to automate.
3. **Keyring persistence across kernel updates.** The `logon`
   keyring type survives a clean reboot but not a kernel-version
   change that re-initializes the keyring slab. Mitigate by
   re-deriving from the seed file on every boot, not by relying
   on kernel-side persistence.
4. **dnsmasq channel-pinning conflict** in router role: in extender
   mode we follow the upstream's channel; in router mode we don't.
   Make sure the channel-selection code paths don't accidentally
   share state.
5. **BadgerDB on a Pi Zero's SD card.** Write amplification could
   matter. Tune `Options.SyncWrites = false` plus an explicit
   periodic flush; sessions are not security-critical past their
   24h TTL anyway.
6. **Update signing key compromise.** The CI signing key is the
   weakest link. Rotate annually; keep the old key as
   secondarily-trusted for a release window. Rescue key is the
   user's backstop.

## Reference / inspiration

- OpenWrt's `uhttpd` self-signed-cert flow — same captive-portal
  download UX we're copying.
- AdGuard Home — full-router mode, similar two-role wizard split.
- pfSense — encrypted-secrets-in-config approach (we're closer in
  spirit to OPNsense's "embed key seed on the FAT partition").
