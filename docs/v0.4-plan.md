# KnotOS v0.4 — Implementation Plan

## Context

v0.1–v0.3 turned a Pi into a working router with a dashboard, ad-block,
per-device profiles, HTTPS, encrypted secrets, signed auto-updates,
and an honest device-presence signal. Functionally we now match a
mid-tier consumer router — minus the bigger feature set, plus a much
nicer UI.

v0.4 takes the next step: stop being only a LAN appliance and start
doing **things consumer routers don't do well, or don't do at all**.
Three flagships, picked specifically because each has a clear
"первый раз сделал — друзьям показал" moment:

1. **Дотянуться до дома из любой точки мира** — встроенный
   WireGuard-сервер с QR-онбордингом. Подключаетесь к домашней сети
   с телефона в дороге одним сканированием экрана.
2. **Принять гостей правильно** — гостевая сеть с QR-пасспортом и
   автоистечением, плюс mDNS-реflector, чтобы гости могли кастить
   на ваш Apple TV / Chromecast не попадая в основную сеть.
3. **Спрятать DNS от провайдера** — встроенный DoH (DNS-over-HTTPS)
   к Cloudflare/Quad9 вместо открытого UDP, переключатель в один
   клик.

Плюс четыре «полезные мелочи», которые ощутимо улучшают
повседневный опыт без отдельного flagship-статуса:

- **Wake-on-LAN** из веб-интерфейса (одна кнопка на странице
  устройства).
- **Bandwidth-per-device** — счётчики через nftables, графики за
  день/неделю.
- **Channel scanner** — сканирование 2.4 GHz, рекомендация
  оптимального канала для AP.
- **Notifications hook** — уведомления в Telegram (и generic
  webhook) на ключевые события: WAN упал, новое устройство в
  сети, расход трафика выше порога.

Out of scope для v0.4 (откладывается в v0.5+):

- **Plugin runtime** (gRPC + lifecycle) — сложно сделать правильно,
  пока не нашёл use-case'а который заплатит сложность.
- **Mesh / multi-node discovery**.
- **DNSSEC validation**.
- **Cloudflare-tunnel-style удалённый доступ к админке**
  (WireGuard покрывает 90% случаев).
- **Time-Machine config snapshots** — сейчас миграции справляются.
- **Speedtest dashboard**.
- **Smart-home интеграции** (HomeAssistant discovery, MQTT) —
  слишком много вариантов, надо сначала собрать обратную связь.
- **Captive portal с кастомным брендингом** — гостевая сеть с QR
  закрывает ту же потребность проще.

## Architecture decisions

### WireGuard road-warrior server

WireGuard уже доступен в ядре Pi OS Lite (`wg-quick`,
`wireguard-tools`). Ставим его как зависимость в base-image,
дальше:

- **На knotd-стороне:** новый пакет `core/internal/vpn/`. На первом
  старте с router-ролью генерирует пару ключей сервера, кладёт в
  `/etc/knot/wg/server.key`+`server.pub` (mode 0600, root-only).
  Конфиг `/etc/knot/wg/wg0.conf` пишется на каждый apply: интерфейс
  `wg0`, listen-port 51820 (или пользовательский), peers
  собираются из `/etc/knot/wg/peers.yaml`.
- **Поднятие интерфейса:** `wg-quick up wg0` или ручной
  `ip link add wg0 type wireguard` + `wg setconf` через
  github.com/vishvananda/netlink (предпочту последнее — чище без
  shellouts). NAT на nftables: `iifname wg0 oifname <wan>
  masquerade`. INPUT-правило: 51820/udp на WAN/LAN allow.
- **Peer onboarding:** UI «Добавить пир» → имя → бэкенд генерирует
  пару ключей на устройстве (приватная отдаётся в браузер один раз,
  как rescue-key из M17b), генерирует `Address = 10.20.30.X/32`
  (где X выдаётся последовательно), формирует client-config:

  ```
  [Interface]
  PrivateKey = <generated>
  Address = 10.20.30.X/32
  DNS = 192.168.42.1   # пиры по DNS идут через knotd-резолвер,
                        # значит per-peer ad-block работает

  [Peer]
  PublicKey = <server pub>
  Endpoint = <wan-ip-or-DDNS>:51820
  AllowedIPs = 0.0.0.0/0   # full-tunnel; toggle в UI на split-tunnel
  PersistentKeepalive = 25
  ```

  Этот конфиг рендерится в QR-код через
  `github.com/skip2/go-qrcode` и показывается в UI.
  Пользователь сканирует с приложением WireGuard (iOS/Android) —
  через 2 секунды у него есть туннель домой.

- **Per-peer policy:** в peers.yaml каждый пир имеет
  `profile_id` ссылку на тот же ProfileRegistry что используется
  для LAN-устройств. Через WireGuard прилетают пакеты с
  `src=10.20.30.X` — модифицируем `dnsDeviceLookup`, чтобы он
  узнавал WG-пиров по их IP так же, как и LAN-устройств по MAC.
  Получаем: ad-block / schedules / DNS-блоклисты работают
  одинаково для домашнего телефона и того же телефона в роуминге.

- **WAN endpoint:** проблема — у домашнего ISP обычно динамический
  IP. Решение для v0.4 минимум: пользователь сам указывает FQDN
  (Cloudflare DDNS, no-ip, и т.д.) в UI; knotd подставляет это в
  поле `Endpoint` client-конфига. Автоматизированный DDNS-апдейтер
  (через Cloudflare API) — отдельный шаг M21b если успеется,
  иначе v0.5.

### Гостевая сеть с QR + автоистечение

На Pi 4/5 с двумя радио — простой случай: гостевая поднимается на
втором phy. На Zero 2W — сложнее, но решаемо: используем
**hostapd multi-BSSID** на одном phy. Современные драйверы
(brcmfmac на BCM43436) поддерживают 2 BSS на один радио — у обоих
свой SSID и PSK, делят канал. Throughput делится, но для гостевой
это нормально.

Каждая «гостевая сессия» — запись в YAML с:
- сгенерированный PSK (12 случайных букв+цифр)
- `expires_at` (по умолчанию 4 часа)
- `bssid` для multi-BSSID режима
- `profile_id` (по умолчанию специальный профиль `guest` с
  блокировкой доступа к LAN и активными blocklists)

UI: «Создать гостевую сеть» → длительность slider (1ч / 4ч / 24ч /
без срока) → бэкенд:
1. Генерирует PSK
2. Перезаписывает hostapd.conf с дополнительной BSS-секцией
3. Генерирует `WIFI:T:WPA;S:<ssid>;P:<psk>;;` строку
4. Рендерит QR (тот же go-qrcode)
5. Показывает QR + текстовый PSK на странице в полноэкранном
   режиме

Через `expires_at` фоновая горутина (ticker 60 сек) убирает
истёкшие сессии: переписывает hostapd.conf, посылает SIGHUP.

**mDNS reflector:** на гостевой сети по умолчанию заблокирован
доступ к LAN (nftables drop в forward chain). Но многие гости
ожидают что смогут "Cast to TV" — для этого мультикаст mDNS
должен пробрасываться между гостевой и LAN. Используем
`avahi-daemon` в reflector mode. Там есть нюанс: reflector
проксирует **только** записи типа `_airplay._tcp` и
`_googlecast._tcp` (whitelist в `/etc/avahi/avahi-daemon.conf`),
чтобы гости не сканировали SMB-шарики.

### DNS-over-HTTPS upstream

Пакет `core/internal/dns/` уже умеет forward на UDP-апстримы.
Добавляем поверх mode переключатель:

```yaml
network:
  dns:
    upstream_mode: doh    # plain | doh
    upstream:
      - https://cloudflare-dns.com/dns-query
      - https://dns.quad9.net/dns-query
```

Для DoH используем `github.com/babolivier/go-doh-client` или
свой минимал (это тонкий клиент: POST application/dns-message,
парсим RFC 8484 ответ). Кэш и query-log работают идентично,
просто транспорт другой.

Преимущество: провайдер видит только TLS-handshake до Cloudflare,
не видит **что именно** мы резолвим. Для российского контекста это
часто и про обход блокировок, не только приватность.

UI: на странице «Защита» появляется dropdown «DNS-провайдер»:
Cloudflare / Quad9 / Google / Custom. Plain UDP остаётся
доступен но помечен «менее приватный».

### Bandwidth-per-device

nftables умеет counter-объекты per-MAC. Расширяем
`BuildNftablesExtender` / `BuildNftablesRouter`:

```
counter byte_<MAC> { ... }
chain forward {
    ...
    ether saddr 11:22:33:44:55:66 counter name byte_112233445566
    ...
}
```

Или проще — через `meta nfacct` (расширение nfacct, есть в стоковых
ядрах). Pi-side: горутина опрашивает `nft list counters` каждые
30 сек, парсит, сохраняет дельту в кольцевой буфер in-memory + на
SD-карту дамп раз в час (чтобы пережить ребут). Размер: 256
устройств × 24 часа × 4 точки в час = 24576 точек × 16 байт = ~400 КБ.

UI: на странице устройства — sparkline за 24 часа, цифры за день
и месяц. На дашборде — «топ-5 потребителей сегодня».

### Wake-on-LAN

Простейшая. Пакет `core/internal/wol/`: формирует магический пакет
(6 байт `0xff` + 16 раз MAC) и шлёт UDP-broadcast на 9-й порт.
Кнопка «Разбудить» на странице устройства, видна только когда
device.online == false. Совпадает с условием на «Забыть устройство»
— расположим рядом.

### Channel scanner

`iw dev wlan0 scan` уже используется для setup-визарда. Парсер
оттуда переиспользуем + новая логика подсчёта весов: для каждого
канала считаем число AP × `signal+90` (более сильные конкуренты
весят больше). Рекомендуем канал с минимальным весом из
{1, 6, 11} (только non-overlapping).

UI: на странице System — кнопка «Сканировать каналы». Показывает
гистограмму загрузки + рекомендованный канал + кнопку «Применить
канал». Применение в extender-режиме — no-op (канал диктуется
upstream'ом); в router-режиме — переписывает AP.Channel в config,
рестартит hostapd.

### Notifications hook

Generic webhook + Telegram preset. Конфиг в `/etc/knot/notify.yaml`:

```yaml
hooks:
  - kind: telegram
    token: "<bot token>"
    chat_id: "123456"
    events: [wan_down, new_device, bandwidth_alert]
  - kind: webhook
    url: "https://discord.com/api/webhooks/..."
    events: [wan_down]
```

Внутренние события — pub/sub через простой Go channel в новом
пакете `core/internal/events/`. Подписчики:
- WAN watcher (расширение существующего `WANStatus` — ловим
  переход up→down)
- Device registry (ловим первое появление нового MAC)
- Bandwidth tracker (ловим превышение порога — пороги
  в profiles.yaml, например `daily_alert_mb: 5000`)

UI: страница «Уведомления» в System: список хуков, добавить /
удалить, тестовая отправка («Test notification»).

## Milestones

Каждый майлстоун — 1–3 коммита.

### M20 — WireGuard server

- `core/internal/vpn/{server,peer,config}.go`: keypair persistence,
  peer registry, hostapd-style config rendering with reload via
  `wg syncconf`.
- `core/internal/api/vpn.go`: `GET /api/vpn/server` (status,
  endpoint, peers count), `GET /api/vpn/peers`, `POST /api/vpn/peers`
  (create, returns one-time client config + QR), `DELETE
  /api/vpn/peers/{id}`.
- `dnsDeviceLookup` extends to recognize WG peer IPs alongside LAN
  MACs so per-peer profiles drive ad-block + schedules.
- nftables: `wg0` interface added to forward chain + masquerade.
- UI: new sidebar item «VPN» → server card (endpoint, port,
  public key fingerprint) + peers list + «Add peer» modal with QR.

### M21 — Guest network + mDNS reflector

- `core/internal/network/linux/guest.go`: hostapd multi-BSSID
  config builder, supervised lifecycle.
- `core/internal/guest/`: session model (PSK, expires, BSSID,
  profile_id), background expiry sweeper.
- avahi-daemon dropped into base-image (`apt-get install`),
  config templated by knotd to whitelist only `_airplay._tcp` /
  `_googlecast._tcp`.
- UI: «Гости» в боковом меню → «Создать гостевую сеть» с
  длительностью + кастомное имя; полноэкранный QR + PSK; список
  активных сессий с обратным таймером и кнопкой «Закрыть сейчас».

### M22 — DoH outbound

- `core/internal/dns/doh.go`: HTTPS POST client, RFC 8484 wire
  format, connection pool. Reuses existing cache+log.
- `Options.UpstreamMode` switch in `core/internal/dns/server.go`.
- UI: dropdown в Защита → DNS-провайдер. Кастомный URL вход тоже
  поддерживается (валидируется как https://<host>/dns-query).
- M22b stretch: DDNS-updater для Cloudflare (per-account API token,
  обновляет A-запись на текущий WAN IP каждые 5 мин).

### M23 — Bandwidth + WoL + channel scanner

Сгруппированы под «полезные мелочи на странице устройства»:

- nftables counters wiring + 24h ring buffer + persisted snapshots.
- WOL package + button on `/devices/[mac]`.
- Channel scanner endpoint + UI gauge на System.

### M24 — Notifications hook

- `core/internal/events/`: in-process pub/sub.
- `core/internal/notify/{telegram,webhook}.go`.
- `core/internal/api/notify.go`: CRUD над хуками + test-fire.
- UI: страница «Уведомления».

### M25 — v0.4.0 release

- Hardware acceptance pass (см. ниже).
- Update CHANGELOG, tag, GitHub release.

## Acceptance test (v0.4.0)

На Pi Zero 2W (extender или router) и Pi 4 + USB-Eth (router):

1. **WireGuard road-warrior:**
   - Открыть System → VPN → Add peer → имя «Phone» → получить QR.
   - На телефоне: установить WireGuard app → сканировать QR.
   - Уйти из дома (отключиться от Wi-Fi). Включить мобильный
     интернет. Открыть https://ip.knot.local в админке устройства
     — должно работать через туннель.
   - На странице Devices теперь видно `Phone (10.20.30.2)` —
     пир с тем же `kids` профилем что и LAN-телефон, ad-block
     работает.
2. **Guest QR:**
   - Создать гостевую сеть «Visitors-4h» на 4 часа.
   - На втором телефоне сканировать QR — телефон автоматически
     подключается к гостевой Wi-Fi.
   - Попытка пинга 192.168.42.1 (gateway) — успешна.
   - Попытка пинга других LAN устройств — drop'ы (firewall блок).
   - На Apple TV (если есть) — гостевой телефон видит её через
     AirPlay (mDNS reflector работает).
   - Перевести таймер на 1 минуту через UI «Force expire after»
     — через минуту сеть исчезает с гостевого телефона.
3. **DoH:**
   - На странице Защита переключить upstream на Cloudflare DoH.
   - Проверить через `tcpdump` на Pi: исходящие 53/udp пропали,
     появились 443/tcp на 1.1.1.1.
   - Защита от рекламы продолжает работать.
4. **WoL:** проводное PC с включенным WoL → выключить → нажать
   «Разбудить» → PC просыпается за 5–15 сек.
5. **Bandwidth:** запустить speedtest с телефона. На странице
   устройства видна вспышка трафика на sparkline. Цифра «сегодня»
   корректна (~ размер speedtest payload).
6. **Channel scan:** в насыщенной городской квартире нажать
   «Сканировать каналы» → рекомендация ≠ текущий → принять →
   AP перезапустился на новом канале → клиенты переподключились.
7. **Notifications:** настроить Telegram-бота, добавить хук
   «новое устройство» → подключить новое устройство к LAN →
   через минуту приходит уведомление в TG.

## Risks and unknowns

1. **Multi-BSSID на BCM43436.** В теории драйвер brcmfmac
   поддерживает, на практике лимит — 4 BSS общий, но реально
   стабильны 2. Если на стенде окажется что 2-я BSS падает под
   нагрузкой, fallback: на Zero 2W гостевая через **rotate-PSK**
   режим (одна и та же AP, временный пароль выдаётся для
   guest-сессии, после истечения PSK меняется обратно). Менее
   изящно но работает.
2. **WireGuard за CGNAT.** Многие домашние ISP в РФ выдают NAT'ed
   IPv4 — incoming UDP не доходит. Mitigation: документация в UI
   с подсказкой проверить «есть ли у меня белый IP» (тест
   `curl https://api.ipify.org` vs WAN IP) и предложить
   обратиться к провайдеру за публичным. Cloudflare-tunnel-style
   обход — стрейнч-цель v0.5.
3. **DoH через провайдера, который блокирует Cloudflare.**
   Российский контекст: 1.1.1.1 иногда замедляется. Поэтому
   несколько upstream'ов в дефолте + UI чтобы пользователь
   подставил свой (например, dot.opendns.com или коммерческий).
4. **avahi-daemon vs knotd-resolver.** avahi и knotd оба бьются за
   mDNS multicast (224.0.0.251:5353). avahi не должен ходить в
   UDP/53, только в 5353; knotd-resolver наоборот не трогает 5353.
   Должно сосуществовать, но проверить отдельно.
5. **nftables counter cardinality.** На сетке с десятками
   IoT-устройств таблица счётчиков растёт. Ограничим: только
   MAC'и из device-registry получают именованный counter,
   остальной трафик в одном bucket «прочее». Безопасный потолок
   ~256 запиcей.
6. **Bandwidth-data на SD-карте.** Запись каждый час → 8760
   операций в год. Износ SD-карты при больших аплоадах не
   стоит. Снимаем по 4 часа батчами + write-coalescing с
   уровня логического слоя.
7. **WireGuard kernel module.** Pi OS Lite arm64 → mainline
   kernel ≥5.10 имеет встроенный wireguard. Не должно быть
   проблемы, но проверить на конкретной версии образа.

## Reference / inspiration

- **WireGuard road-warrior:** patterns from
  [wg-easy](https://github.com/wg-easy/wg-easy) (Docker
  appliance) — мы делаем то же самое нативным процессом knotd.
- **Guest QR + auto-expire:** концепция из Apple's «Open Wi-Fi
  network from password» в iOS, плюс UI inspired by
  [PiVPN](https://www.pivpn.io/).
- **DoH:** упрощённая версия паттерна
  [AdGuard Home](https://github.com/AdguardTeam/AdGuardHome)
  для upstream-выбора.
- **Bandwidth-per-device:** уровень детализации как в
  [Vnstat](https://humdi.net/vnstat/), визуализация а-ля
  [Eero] / [Unifi] dashboards.
- **mDNS reflector:** многострадальный паттерн
  https://wiki.archlinux.org/title/Avahi#Avahi_aliases для
  cross-VLAN airplay.
